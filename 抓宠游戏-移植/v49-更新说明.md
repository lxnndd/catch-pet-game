## 三、顺手修掉的两个隐藏 bug

这两个都是「全队共享」这个改动**逼出来的**（写验收时才发现）：

### bug 1：进化会把倒下的宠「复活」

`runEvoCheck()` 里原本是：

```js
p.sp=to; p.pp=null; p.ppSp=null; p.hp=maxHpOf(p);   // 一律回满血
```

进化补满血本身是合理设计（种族值提升、上限跳升），但它**遍历的是全队** —— 所以一只 HP=0 的宠只要在战斗中升级到进化等级，就会**自动满血复活**。

**修法**：进化前记住它是不是倒下的，倒下的保持倒下。

### bug 2：边遍历边判断 `hp`，名单会中途变化

第一版 `gainExpTeam` 是「遍历队伍 → 见到 `hp<=0` 就跳过」。但 `gainExp()` 内部会触发 `runEvoCheck()`（遍历全队、可能改 hp），于是：

```
循环到 1 号（出战宠）→ 发经验 → 触发进化检查 → 2 号的倒下宠被进化"补满血"
循环到 2 号 → p.hp<=0 已不成立 → 它混进了分配名单 ❌
```

**修法**：进入循环前先**快照参与名单**（`hp>0 && lv<100`），再逐个发经验 —— 不再依赖遍历途中的状态。

> 验收里能看到这个过程的痕迹：修之前「倒下的 +30、参与 2 只」，修之后「倒下的 +0、参与 1 只」。

## 六、本批新增的坑

63. **「补满血」这种善意设计会在别处变成 bug**：进化回满血是为了让玩家不亏，但它遍历全队 + 无条件执行，于是「倒下的宠升级到进化等级就自动复活」。**教训**：遍历全队的批量操作里，任何"恢复到满状态"都要先判断对象当前是否处于特殊状态（倒下/异常），否则会悄悄修复掉本该保留的状态。
64. **遍历中读可变状态 = 名单会在半路变化**：第一版「边遍历边判断 `hp`」看起来天经地义，但被调用的 `gainExp` 会连锁触发 `runEvoCheck`（改 hp），于是前面的操作改变了后面元素的判断条件。**教训**：循环体里如果调用了"可能修改被遍历集合"的函数，先在循环外**快照**出要处理的名单 —— 这类 bug 只在特定顺序下出现（本例要"出战宠先发经验 + 后面正好有只倒下的宠卡在进化等级"），极难复现。
