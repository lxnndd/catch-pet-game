## 一、复核结论：那 31 点是怎么来的

**先看两个数字的真实构成**（脚本逐层打印）：

| | 小火焰猴 Lv7 | 够赞狗 Lv8 |
|---|---|---|
| 属性 | 火 | 毒 / 格斗 |
| **种族总和** | **309** | **555**（传说级宝可梦 Okidogi） |
| 实战特攻 / 攻击 | 15 | 27 |
| 实战防御 / 特防 | 13 | 21 |

- **火花（威力40·特殊）**：特攻 15 ÷ 对方特防 21 = 0.71 → 核心 `floor(floor(4.8×40×0.71)/50)+2 = 4` → ×1.2 ≈ **5.6 点**（截图 4 点，合理范围）
- **咬住（威力60·物理）+ 攻击↑1**：攻击 27 ÷ 我方防御 13 = **2.08** → 核心 `floor(floor(5.2×60×2.08)/50)+2 = 14`

**问题就出在最后一步**：`14 × 1.2 × 性格 × …` 本该是 **17 点**左右，但实测打到 **31 点** = 我方 HP 37 的 **84%**。

## 二、三个问题（一个是我引入的 bug）

### ① `A/D` 被乘了两次（v47 引入，主因）

```js
var _core = Math.floor(Math.floor(_lvTerm*mv.power*statMul)/50)+2;   // ← 官方主体里已有 A/D
var atkM  = atkT.atk*statMul;                                        // ← 这里又乘一次 ❌
var base  = _core*DMG_K*e*atkM*…;
```

等于实际用的是 **A/D²**。本例 A/D = 2.08，伤害就被额外放大 2.08 倍。

**修法**：`atkM` 只保留性格倍率 —— `var atkM=atkT.atk;`（面板比值只在 `_core` 里出现一次，与官方公式一致）。

### ② 「攻击↑1 完全没效果」的假象（85% 上限掩盖）

修之前测「攻击↑1」：平均 **31.0**，而没加状态是 **30.9** —— 看起来能力等级失效了。

真相是：**两个值都被「单次伤害 ≤ 目标血上限 85%」削平了**（37 × 0.85 = 31.45 → 取整 31）。
伤害早就冲到上限以上，所以再怎么加攻击都看不出来。

修复后：

| 咬住 | 无能力等级 | 攻击↑1（×1.3） |
|---|---|---|
| 修复前 | 30.9（撞上限） | 31.0（撞上限） |
| **修复后** | **17.3** | **22.2（×1.28 ✅）** |

### ③ 克制提示「效果不理想」是**被最差那招带偏的**

小火焰猴对毒/格斗各招的倍率：

```
抓（普通） 1×     瞪眼（普通） 1×     火花（火） 1×     挑衅（恶） 0.5×
```

`typeEdge()` 原来的逻辑是「只要技能池里有任何一招效果差，就报 ⛔ 效果不理想」——
于是玩家看到「我方技能对它 效果不理想」，会以为整只宠都打不动，其实火/普通都是 1×。

**修后**：以**最好的招**为准给结论，若确实有更差的招再补一句：

```
➖持平（注意有效果不理想的招）
```

## 六、本批新增的坑

65. **「伤害上限」会把上游的 bug 藏起来**：`A/D` 被乘两次后伤害冲到 34.9，正好撞上「≤85% 血上限」被削成 31 —— 表现完全正常（甚至更难），只有把上限去掉、或不撞上限的场景才看得出。**教训**：削峰机制（上限/钳制/取整）会让「超标」看起来像「设计如此」；排查数值异常时要**同时打印「未削峰的原始值」**。
66. **改公式时要清点每个系数出现在哪几项里**：v47 我把 `statMul` 加进 `_core`（官方主体）时，忘了 `atkM` 里还留着一个 —— 单看任一行都"对"，合起来才是错的。**教训**：像 `A/D` 这种核心比值，改完用 `grep` 数一下它在整个函数里出现了几次，期望值应当与官方公式一致（本例只该出现 1 次）。
67. **提示类文案取「最好」还是「最差」要写明白**：`typeEdge` 里 `best` 与 `worst` 都在算，但输出规则是「有差招就报差」—— 于是玩家以为整只宠都不行。**教训**：面向玩家的"综合评价"应以**最优解**为口径（"你能打出什么效果"），把坏消息降级为附注。
